# Working notes for Claude

Conventions that are load-bearing here and not obvious from reading the code.

**The reasoning behind a decision lives in the comment above it.** File headers and function docstrings in `src/*.gs` carry the *why*, deliberately and at length — including what was tried and rejected. Read the header of the file you're changing before changing it, and **don't re-litigate a decision it already argues.** If you disagree with one, say so; don't quietly reverse it.

(An earlier `docs/PLAN.md` held the original design document and build plan. It was removed once every phase shipped — it had become a historical artefact that read as a roadmap. `git log -- docs/PLAN.md` if you ever want it. A second one covered the dashboard rebuild, the reports tab and the review queue, and a third the mobile web app; all three were removed the same way when they landed.)

## The governing rule

> **Code only for what runs unattended and repeatedly. One-time human operations get documented, not automated.**

This is why there's no CSV importer (File → Import, then paste-values) and no "add manual account" wizard (you type a row). Both were removed deliberately. Don't reintroduce them; if a new feature is one-time, write it into `docs/` instead.

The one accepted exception is `installCredentials()`: a documented procedure that silently corrupts a multi-line PEM is a trap, not a procedure.

**19 is no longer last, and that is fine** — it names its items as strings and filters them through `functionExists_`, so load order was never what made it work. What it does mean is that a menu item for something in 20–23 appears by itself, exactly as every earlier phase's did.

**Where the mobile seam is:** 21 reads and 22 writes, and neither is reachable from a browser — every function in both ends in `_`, which Apps Script enforces as private to `google.script.run`. 23 is the entire public surface, and `tests/app.test.mjs` holds it to that by reading the files rather than by remembering.

The gap before `18` is deliberate — adding a phase should not renumber anything. It got used, and by **two** files: analytics and review are different kinds of thing (one reads, one writes back) and splitting them was cheaper than a 900-line file. Two names at the same number is fine because the numbering is load order, and `17_analytics.gs` sorts before `17_review.gs`, which is the dependency direction. It is not licence to keep adding — a third would mean 17 has become a bin.

**Where the charts seam is:** a chart is configuration pointed at a range, so charts are built after every formula that fills one. That used to span two files — 16 wrote the blocks and exposed `DASH` for 17 to point at — and now sits entirely in `17_analytics.gs`, which both writes the `reports` blocks and plots them.

**The two read-only tabs are gone, and that was the point of the app.** `dashboard` and `recent` answered "what is my position" and "what happened lately" in a grid renderer that had to open 4,600 rows and fifty array formulas to do it. The phone answers both without either tab, and `appDashboardData_` deliberately *computes* its numbers rather than reading cells off a tab — so nothing depended on them when they went. `reports` stays: it is the only independent implementation of the same aggregates, and two implementations that agree is the only evidence the numbers are right.

When a file starts holding two kinds of thing, split it before adding a third. `04_auth.gs` reached 769 lines by owning the consent flow, the accounts domain, the sheet primitives and the diagnostics at once; the primitives in particular were invisible there, and the sync would have grown its own copy.

## After pushing code

`npm test` → `npx clasp push --force` → **say whether a redeploy is needed.**

`clasp push` updates the Apps Script project, so menu items and anything run from the sheet pick it up at once. It does **not** update a live `/exec` deployment, which serves a frozen version. Anything touching `doGet`, `src/page.html` or `20`–`23` needs:

> Manage deployments → pencil → Version: New version → Deploy

**There are two deployments and they are not interchangeable.** Door 1 is the consent redirect, access **Anyone**, and its URL is registered with Enable Banking. Door 2 is the app, access **Only myself**. Both have to be updated, and the trap is in the access setting rather than in remembering:

- *New deployment* mints a different URL. On Door 1 that breaks the registered redirect; on Door 2 it just means the home-screen icon points at a dead URL. Always update in place.
- **A Door 2 redeployed as "Anyone" serves bank balances to anyone with the URL.** The owner gate is what stops that being fatal, and a lock behind a door you left open is not a thing to rely on. When a redeploy is needed, say *which* door and *what its access setting must be* — not just "redeploy".

Flag all of this explicitly when a push needs it — don't leave it to be discovered as a Drive "unable to open the file" error, or worse, not discovered at all.

## Constraints that break things quietly

- **No `import`/`export` in `src/*.gs`.** Apps Script concatenates files into one global scope; the tests load those exact files via `node:vm`. An export would make a function reachable from a test and break it for every user. CI greps for it.
- **File numbering is load order.** Apps Script has no modules and sorts by name.
- **Author formulas with commas and write them through `setFormula_()`.** Decimal-comma locales (it-IT and friends) need `;`, and `setFormula()` does not convert — a comma form lands as `#ERROR!`. `localizeFormula()` translates once at the write boundary.
- **`oauthScopes` are explicit**, so a missing one fails at the moment of the call. `tests/manifest.test.mjs` derives the required set from what `src/` calls — add a service and add its scope, or CI fails. It also fails on scopes nothing uses.
- **`getLastRow()` is not a record count.** Several tabs carry an open-ended `ARRAYFORMULA` in row 2, so Sheets reports ~1000 rows of content on a tab holding nothing — which once put a real account at row 1001 while every run reported success. Never append at `getLastRow() + 1`; use `appendRows_` (strictly after the last record) or `nextEmptyRow_` (upserts, reuses a gap). `sheet.appendRow()` has the same bug baked in and the harness reproduces it faithfully.
- **An empty cell is not zero. Call `isBlankCell_` *before* `Number()`.** `Number('')` is `0` and `isFinite(0)` is true, so the obvious guard passes and a cleared cell reads as a value someone deliberately typed. This has bitten four times now: a cleared `sync_window_days` fetched nothing while looking like a healthy sync, a blank cash amount became a €0 transaction, a cleared `sync_hour` scheduled midnight. Every one failed silently *and* plausibly — which is why the rule is check the input, not the result. `parseFloat` and `parseInt` are the same. Treat any new numeric read of a cell as suspect until it has a blank test.
- **A boolean column an `ARRAYFORMULA` builds must say `FALSE` on the empty rows, not `""`.** `QUERY` infers a column's type from what is in it, and an `ARRAYFORMULA` spills to the *sheet's* last row rather than the last record. Thirty booleans among nine hundred empty strings is a **text** column, so `where AC = true` matches nothing — on the newest books, which are exactly the ones where a blank dashboard reads as "not set up yet" rather than as a bug. `in_reports` is the column this applies to; the other derived columns emit `""` correctly, because a blank number is not a false number.
- **A conditional-format rule does not pass through `localizeFormula`.** That helper translates the formulas written into *cells*, at the one boundary they all cross. `setConditionalFormatRules` is not that boundary, so `=AND(a,b)` in a decimal-comma locale is a parse failure with no cell to show `#ERROR!` in — the rule simply never fires and the thing it was watching goes on looking fine. Write such a condition with **no comma at all**: two tests multiplied and compared to zero needs no separator and returns a real boolean.
- **A formula that will be compared to `TRUE` must return a boolean, not `1`.** Sheets does not coerce across types in a comparison: `=1=TRUE` is FALSE there, where in Excel it is TRUE. A condition built by multiplying two tests yields `1`, so `include=TRUE` silently misses and every column gated on it blanks. The symptom is two columns contradicting each other — `include` showing `1` while `why` gives the excluded-row reason — because only one of them is comparing types Sheets thinks are comparable. End such an expression with a comparison (`(…)>0`).
- **A generated sheet reference needs its `!`.** `TABS.IMPORT_RAW + '$A$2:$A'` reads correctly at the call site and produces `_import_raw$A$2:$A`, which does not parse. Build the whole reference in one helper rather than leaving a bare range for callers to prefix. Both this and the rule above shipped green: the harness never hands a formula to a spreadsheet, so parens, quotes and localisation were all it could check. `tests/import.test.mjs` now checks reference shape and result type too — the two things a string test *can* prove.
- **Never write a literal control character into a source file.** A `join('\0')` written as a real NUL byte works perfectly at runtime — and makes `grep` classify the file as binary and report *nothing*, silently. Two separate wrong conclusions came from that: "no formula builds column J" and "the balance `ARRAYFORMULA` doesn't exist", both drawn from an empty grep over `04_setup.gs`, which contains eleven of them. Write the escape, not the character. This has now happened twice — most recently in the very test written to catch it — so it is a test rather than a rule: `tests/manifest.test.mjs` fails on any control character under `src/`. `file src/*.gs` reporting `data` rather than `text` is the manual check.
- **A second definition of a function name silently wins.** Apps Script concatenates `src/*.gs` into one global scope, so two `function needsReviewFormula()` in the same file is not an error — the later one replaces the earlier, and every existing caller quietly changes meaning. It happened by adding a dashboard block whose formula builder reused a name the health strip was already using, which would have put a ten-row `QUERY` where a count belonged. `grep -c 'function name('` before naming anything, and prefer a name that says which block it builds.
- **The schema grows rightwards and so do you — into the same column.** "Append to the right is safe" and "a new schema column lands on the first free column" describe the same slot. `buildTable_` wrote the header row straight over it, which cost the name of that column *and* the new formula: an `ARRAYFORMULA` anchored at row 2 cannot expand through a column that already has data and gives `#REF!` instead — one broken formula on one tab, one header quietly renamed, and nothing connecting them. `in_reports` shipped green and landed as an empty dashboard on the only book that mattered. `makeRoomForNewColumns_` now inserts a column when the slot is occupied. Test **against a book that already has data in that slot**, not just a fresh one — the harness builds every tab from nothing, where the collision cannot happen.
- **`INDEX` does not vectorise inside an `ARRAYFORMULA`; `VLOOKUP` does.** `INDEX(A:A,MATCH(x,B:B,0))` returns a single value however tall `x` is — the first row's answer repeated down the column, correct on row 2 and wrong everywhere below, which reads as working. Crossing a tab from a key to a value therefore needs the key *left* of the value, and `VLOOKUP` cannot look left. That is why `categories` carries `child_key`/`child_parent`: `subcategory` and `category` copied into that order, purely so one vectorised lookup can cross them. Two copied columns are the cheap answer; a cleverer one does not exist here.
- **A subcategory's name has to identify exactly one parent.** `category` resolves a `subcategory_override` through a `VLOOKUP`, which takes the first match and says nothing about the second — and `child_list`, the range every subcategory dropdown points at, is `SORTED(UNIQUE(...))`, so two parents sharing a child name collapse to one indistinguishable entry *before* the lookup is reached. The seed shipped with two (`Home` under Shopping and Insurance, `Books` under Shopping and Education); both were renamed rather than disambiguated, because "which Home did you mean" is not a question a dropdown can ask. A test holds the seed to it and a smoke test holds the live tab to it, since `categories` is the user's to extend and `Other` under everything is the natural way to extend it.
- **A wholesale rewrite must stop at the stored columns.** `clearDataRows_(sheet, key, WIDTH)` clears from row 2, so passing the full schema width erases every ARRAYFORMULA anchor on the tab — and writing the records back at that width stores the values those formulas had spilled into the space they would expand through. The column ends up formula-less *and* full, which a later `setFormula_` cannot fix: the anchor comes back and is refused expansion. `removeRetiredCategories_` did this to `categories` because its comment said "there are no formulas on this tab", true when it was written and false since `parent_list` was added. One run cost every category dropdown its source, and the repair was a sheet edit rather than a re-run. Schemas with both kinds of column now say so — `CATEGORY_COLUMNS_STORED`/`_DERIVED`, as `transactions` already split at O.
- **Renaming a seed row is a migration, and `RETIRED_CATEGORIES` is where a migration goes.** `setup()` adds seed rows and never removes them, so a rename *appends* the new name and keeps the old one — the tab ends up holding both. Renaming the two duplicate children therefore left every existing book with exactly the collision the rename was for, and the smoke test went on failing with nothing in the code left to fix. The unit tests all passed, because the seed they read was correct; only a book that had already been set up could show it. Two further traps once an entry is written: a rename keeps its parent, so reading `to[0]` as a move makes the parent look like it moved to itself (`retiredParents_` exists for this), and a `subcategory_override` holds a bare child name, so a rename whose old name survives under another parent **cannot** be applied — report those and leave them.
- **A grouped `QUERY` must group by every non-aggregate it selects, *verbatim*.** `select year(D), month(D)+1 … group by year(D), month(D)` is rejected whole — `month(D)+1` is not `month(D)` — so the correction for QUERY's zero-based `month()` cannot live in the select list. It goes in the formula that formats the label, where it is arithmetic on a cell and groups nothing. The monthly report block never produced a row from the day it shipped, and a test asserted the broken arrangement was deliberate. This is one of the few formula bugs a string test *can* prove, and `tests/analytics.test.mjs` now proves it.
- **An `IFERROR` must not name a cause it did not check.** The reports blocks fell back to `"nothing matches those filters"`, which is one of the two things that produce no rows; the other is a malformed query. A block that had never once worked reported an honest-looking empty result through six smoke-test runs, and the chart-has-data check agreed with it — `nothing to plot` is exactly what an empty result looks like. If a fallback cannot distinguish the cases, it has to say so and point at the cell that would.
- **A spilled cell and a cell someone typed are indistinguishable through the API, and renaming a column is what makes that matter.** `getValues()` returns the computed value for both; `getFormulas()` returns `''` for both, because only the anchor holds the formula. `makeRoomForNewColumns_` asserted the opposite — "an array of ours that expanded leaves computed cells, never stored ones" — and so read a live spill as a user's data. Reaching it needed a *rename*: `recordNewColumns_` calls a column new when its name is absent from the header row, so `amount_eur` → `amount_base` presented a working, spilling column as a new one, and the code inserted a column to get out of the way of its own output. Two inserts later every derived column sat one place right of its header — the one edit `transactions` cannot survive — and it presented as three unrelated smoke-test failures on a live book with 4,600 rows. **The anchor is the only evidence there is: a formula in row 2 means the column is ours, and the rows below must not be consulted at all.** Treat renaming a schema column as a migration, not an edit.
- **A conditional-format rule may not contain a comma, which rules out every function you would reach for.** `AND`, `IF`, `OR` and `VLOOKUP` all need one. The dashboard's answer is a hidden severity column: a formula in a *cell* — which does pass through `localizeFormula` — computes `2`, `1`, `0` or blank, and every rule is `=$G4=2`. That also puts the thresholds in `_config` rather than freezing them as literals inside a rule no test can evaluate. Reach for a hidden helper cell before reaching for a cleverer rule.
- **A layout decision made for the desktop has to be re-checked against the phone.** The dashboard's blocks were separated by *column* so a growing `QUERY` could not collide with its neighbour — correct reasoning, and it produced a tab twenty-nine columns wide on a device that scrolls vertically. The fix was not to abandon the guarantee but to get it a cheaper way: bound every block with an explicit `limit` and stack them. When a constraint forces an awkward layout, ask whether the constraint can be removed at the source.
- **A control the phone renders natively can ignore `width`, and Chromium will never tell you.** `input[type="date"]` on iOS Safari sizes to its own content while the native appearance is on, so `.field { width: 100% }` was honoured by every browser this was built in and silently dropped by the only device it is for: two of them side by side put the second half off the right edge. That overflow is also where "the view slides sideways and shows white" came from — the document was genuinely wider than the phone, and the white behind it is Apps Script's own wrapper page, which the iframed document cannot paint. `-webkit-appearance: none` is the fix for the input; `overflow-x: clip` and `overscroll-behavior: none` on `html` are the belt for anything that overflows next. **Verifying mobile-only CSS in a desktop browser proves the rule is applied and cannot prove the bug is fixed** — say which of the two you did.
- **A chart drawn with `preserveAspectRatio="none"` cannot carry its own labels.** Both charts fill their card by scaling a 100×40 viewBox, which multiplies x by ~3.5 and y by ~3; `vector-effect="non-scaling-stroke"` rescues the strokes and nothing rescues a glyph, so an SVG `<text>` would be stretched by different amounts on each axis. The scale is therefore HTML in a gutter beside the plot, positioned from viewBox units through one stated `40 units = 120px` conversion rather than by measuring after layout. **A plot with a truncated baseline and no scale reads as starting from zero** — a net worth that moved 13% drew from the floor of the card to its ceiling, and captioning both ends with their own value says where the line began and ended while still saying nothing about what the height between them is worth.
- **A blank in a seed is a question, not a default, and nothing can diverge from it.** `reportSeedDivergence_` compared the whole row past the key, so `_config`'s three deliberately-empty rows — `alert_email`, `owner_email` — reported a divergence for the act of being answered. Filling in an alert address would have logged "1 seeded row differs from the defaults" to `_anomalies` on every run for ever, and `applySeedDefaults` would have offered to blank it back. `owner_email` is what exposed it, because `setup()` fills that one itself and so every book would have carried the noise. `seedRowDiffers_` is the one comparison both halves now use — they must agree, or "Update mappings to defaults" changes something it never listed.
- **A function reachable from `google.script.run` is one whose name does not end in `_`.** That convention is *enforced*, not decorative, which is what makes it a security boundary rather than a style: everything in `21_query.gs` and `22_actions.gs` is private by name, and `23_api.gs` is the entire surface a browser can reach. The realistic failure is *another* entry point added later without `requireOwner_()`, so the guard is a test that reads the file and derives the list, rather than a list someone maintains — and for the same reason this sentence no longer says how many there are, having twice said a number that had stopped being true.
- **A faked enum must have exactly the members the real one has.** `setXFrameOptionsMode(HtmlService.XFrameOptionsMode.IFRAME)` shipped green: `IFRAME` belongs to `SandboxMode`, a different and vestigial enum, so the argument is `undefined` in production and the call takes the app page down for the only person allowed to open it. The harness passed because its stub had invented an `IFRAME` member. A fake of an enum exists almost entirely to fail on a typo, and one that answers for a member the real thing lacks cannot. Same rule as the `DriveApp` fake refusing everything — be no more forgiving than the real thing, which is now the third time that direction of error has cost something here.
- **`drive.file` is a REST-API scope, and `DriveApp` cannot use it — so the fix for a Drive permission error is almost never a wider scope.** The Apps Script service is documented against full `drive`, the whole Drive; `drive.file` means per-file access to what this script created, which only the REST API can express. The snapshot was written against `DriveApp` and refused: first `createFolder`, which was "fixed" by falling back to `createFile`, which is refused for the identical reason. The weekly trigger then failed on **every** run for months, mailing each failure to the same address as every other alert, with nothing in the book disagreeing. Two things generalise. **An error naming one method is evidence about the service, not about the method** — the fallback was chosen because the message said `createFolder`, and the message says whatever you called first. And **a backup is the one feature whose failure has no other symptom**: nothing downstream of a snapshot ever reads it, so it can be broken from the day it ships and look exactly like a working one. `checkSnapshotPermitted_` in the smoke tests is the answer — it writes a probe file and deletes it, because whether Google permits a write is a fact about this book's consent and no fake has scopes to be short of.
- **A scope is permission to use an API; it does not switch that API on.** Two independent gates, failing with messages that read alike, and the snapshot hit them one after the other — the fix for the scope shipped, passed, and came back *"Google Drive API has not been used in project 000000000000 before or it is disabled"*, which reads as a permissions error and sends you to the scope list, the one place with nothing wrong. Two things to know before reaching for the console link in that message. **This script's Cloud project is a default one** — no `projectId` in `.clasp.json` — and the console will not open a default project, so Google's own suggested fix is a dead end here. And **declaring an advanced service in `appsscript.json` is what enables the API**, because Apps Script switches it on in a default project for a script that depends on it. That is the whole reason `12_monitor.gs` calls `Drive.Files` rather than `UrlFetchApp` against the identical REST endpoints: equivalent at the call, and only one of them arranges to be allowed to make it. The manifest also pins the version, and v2/v3 disagree on the method names (`insert`/`delete` against `create`/`remove`), so `tests/manifest.test.mjs` holds the source to the version the manifest declares.
- **A rule written out quoting the thing it forbids defeats its own guard.** `page.html`'s comment said "nothing is built with `innerHTML`", and the test that fails on that token in any `src/*.html` failed on the comment. Identical to the control-character rule, which was first written into this file *quoting the character it warns about* and made itself ungreppable. Write the rule, not the token — it happens every single time.
- **One timing is not a measurement, and `getValues` is the reason.** Reading the same 4,615 rows took 2,025ms, 3,254ms and 9,418ms on the same book within an hour. A single sample of a spreadsheet read carries a variance wider than most of the differences worth acting on — so two samples taken minutes apart will "show" whatever you were hoping for. This has now produced two wrong conclusions in one session: that a narrow read was a 20x saving (it was 93% slower), and that the ledger cache added 7.4 seconds to a miss (it adds ~360ms; the rest was the read varying). **Time the parts separately and compare them within one run**, where they see the same conditions — `describeQueryCost` reports `sheetMs`, `serialiseMs`, `storeMs` and `parseMs` for exactly that reason. A before-and-after across two runs proves nothing here.
- **Count the round trips before optimising the big one.** The narrow-read experiment already proved a `getValues` costs the *call* rather than the cells, and that conclusion was then applied only to `transactions` — the one read that was easy to see. Opening the app made **35 of them over about 7 distinct tabs**: `readRecords_` is *two* calls (`lastRecordRow_`, then the block) because `getLastRow()` lies on any tab with an `ARRAYFORMULA`; `readConfig_` is not memoised, so each of its ~eight callers pays a fresh pair; `accounts` was fetched four separate times by four functions that each went and got it. Measured: `bootstrapMs` 6,170 with the ledger already cached, ~175ms a trip, and **the ledger was 315ms of it**. Caching the single largest read and leaving thirty-four others in place is exactly why the ledger cache landed, worked precisely as measured, and changed nothing the user could feel. `withReadCache_` in `03_sheets.gs` now shares reads for the length of one request — **opt-in**, because `setup()` and the sync write a cell and read it back and an always-on memo turns that into a silent stale answer. Only read-only app requests switch it on, which is the 21-reads/22-writes seam that already exists.
- **A fix that does not move the number has two explanations, and timing tells them apart in neither.** "The cache never engaged" and "the cache engaged and was not the bottleneck" produce an identical slow screen and identical milliseconds. Instrument the *mechanism*, not just the clock: `LEDGER_SOURCE` says `cache` or `sheet`, and `describeDashboardCost` reads the ledger twice back to back — cache dropped first — so the second read is precisely the case being complained about. A diagnostic that reports only durations can confirm a problem and can never locate one.
- **"Faster" and "feels faster" are different targets, and only one of them is what was asked for.** Server time on the app's first screen went 6,200ms → 2,400ms across four separate fixes, every one of them real and measured, and the answer to "is it fast now" was still *no*. **What a person experiences is when the first real content appears, not when the last does** — and a single call behind a single spinner makes those the same moment by construction. The dashboard's top half (net worth, tiles) needs no ledger and cost ~800ms; it was waiting ~1,600ms on the half that did. Two calls in parallel, each block drawing as it lands, costs ~500ms more in total and starts the screen 1,600ms sooner. Before optimising a total again, ask what the screen could already be drawing.
- **A number measured on the server is not the number the user is waiting on, and on this platform it is the small half.** Profiled from outside the sandboxed iframe (Playwright over CDP against the live deployment — the only vantage point that can see any of this): the `/exec` document alone takes **~3,350ms**, being Apps Script's container spin-up plus `doGet`, before a line of page code runs. Then every `google.script.run` call costs **~2,700ms of fixed overhead**: `appOpen` does ~800ms of server work and takes ~3,500ms from the browser, twice in a row within 10ms of itself. So a ~7s open is ~800ms of this project and ~6,000ms of Google. Server work still mattered — halving `appBootstrap` took ~5s off the open — but past this point **the lever is fewer round trips, not faster ones**, and the floor is roughly six seconds no matter what the code does.
- **`doGet` is a free ride for bounded work and a trap for anything else.** It is already an execution paying the ~3,300ms startup, so work moved into it costs only the work — which is why the first screen is templated into the document (`appInlineBoot_`) and its round trip disappeared, ~2,000ms, more than every server-side fix before it combined. The same reasoning applied to the *lower* half made the document three to seven times slower (3,116/3,351/3,686ms → 5,875/7,030/**23,928**ms) even with the ledger warm, because everything it does lands in front of a page with nothing on it yet. The rule that survives: **bounded and small, or it goes in a round trip.** `appOpenData_` reads three tabs and is ~800ms whatever the ledger holds; `appOverviewData_` touches the ledger and is not.
- **Price a prefetch against the round-trip floor, not against zero.** `appOverview` carries the first view of Records because it already holds the rows — measured best-of-two with `appOpen` (1KB, ~800ms) as the floor: `appRecords` 2,225ms for 33KB, *below* the floor, so its filter-sort-slice is free; `appAnalytics` 3,045ms for 2KB, ~800ms of `balanceSeries_` walking the whole ledger. So Records is prefetched and Charts is not. The estimate that preceded this said "~10ms for both" and was wrong by two orders of magnitude — and the owner had already said which screens they open, which agreed with the number and came first.
- **Do not infer a client-side cause from a server-side symptom; profile the page.** Two conclusions this session were drawn from watching the app and reasoning: that concurrent calls contend (they do not — parallel beat sequential 3,916ms to 7,710ms on total, with first paint within 400ms), and that the deployment was serving current code (it was serving a version cut before the split, so the app and the menu diagnostics were two different builds all day). Both were settled in minutes by attaching a browser to the live URL and reading the waterfall. `clasp deployments` tells you the version a door is serving, and grepping the served page for a function name tells you which build it is — do that *first* when the app disagrees with the numbers.
- **A cache TTL is a claim about how often the thing is used, and that is not a claim you can reason your way to.** `LEDGER_CACHE_SECONDS` was 300 for a defensible reason — the version counter cannot see somebody typing into `transactions`, so let the expiry be the backstop and five minutes is cheap to be wrong by. What it never asked was how far apart two opens of the app are. A hit needed two inside five minutes; nobody opens their finances twice in five minutes; so `ledgerFirst` came back `"sheet"` on run after run and the cache existed without ever being used for the thing it was built for. **When a TTL is set as a backstop for an invalidation you did not implement, you are paying for the miss on every use — close the hole instead.** `onEdit` bumping the version on any `transactions` edit is what let the TTL go to six hours, and `LEDGER_SOURCE` in the diagnostic is the only reason the problem was visible at all.
- **Time the parts in the order they actually run, sharing what they actually share.** Timed one at a time, each part pays for whatever nobody fetched before it — so the *first* one looks expensive and every part after it looks free, whoever they are, and the ranking is an artefact of the order you wrote the diagnostic in. `describeDashboardCost` therefore reports the parts twice: separately, which prices the duplication, and again inside one `withReadCache_` in bootstrap order, which is the only arrangement where "this part is still slow" means it is reading something nothing else did. That second pass is what found `checkRowLoss_` scanning 4,614 rows for a number `ledger.length` already held — 40% of the screen, hidden inside a health check whose other five detectors cost ~300ms between them.
- **A diagnostic is scoped to the thing it was written for, and stops being evidence one layer out.** `describeQueryCost` prices a ledger read, honestly and well; it was then quoted for how long the *app* takes to open, which it has never measured — every `_config`, `accounts`, `_status`, `_runs` and `categories` read on that path is invisible to it. Ask what a number was actually taken over before reusing it as an answer to a wider question.
- **The bank is an untrusted input, and `setValues` does not write text — it writes what someone typing that string would get.** Every guard in this project watches the *browser*: `requireOwner_`, the `_`-suffix rule, `htmlSafeJson_`. The provider was trusted throughout, and it is the one source that is neither the owner nor gated — `remittance_information` is free text the **sending** party fills in, so anyone who knows the IBAN can send a euro cent and choose what column I says. A description beginning with `=` lands as a live formula, evaluated server-side with this book's own access, and `IMPORTDATA` fetches with no consent prompt where `IMPORTRANGE` asks for one: the first sync after the transfer ships the ledger out and looks like an ordinary run. `textSafe_` in `03_sheets.gs` prefixes an apostrophe — Sheets' own "this is text" marker, consumed on write and absent from `getValue`, so the round trip is lossless — and it sits at `writeCell_`, `toRow_`, `appendRows_` and `writeStagedColumn_` rather than at the point any one field is built, because the danger is a property of writing to a cell. It cannot collide with an intentional formula: those all go through `setFormula_`, which is a different call at every site. Two things that are not obvious. It must test `typeof value === 'string'`, or a negative **number** collects an apostrophe and lands as text, which is every total skipping the row. And the harness had to learn to consume the apostrophe too — a fake that stored `'=x` would pin a value no book has ever held, the `IFRAME` failure in the other direction.
- **Bulk writes go through one `setValues`.** A per-cell loop is fine for `accounts`; at a few thousand transactions it burns the six-minute limit on round-trips alone.
- **`transactions` is never sorted, and no column is ever inserted mid-schema.** Both break row identity and every formula reference silently. Append to the right is fine — that is why `connection_id` is the last `accounts` column rather than sitting next to `provider`.
- **Code owns `transactions` A–O; formulas and the user own P onward.** Sync appends, never rewrites. A row already in the sheet is never touched again.
- **`description` is the one A–O cell anything edits, and only on a row no bank will fetch again.** Everything else the app writes goes to an override column, which exists so your opinion and the bank's can both sit on the row; `description` has none, so changing it changes the stored value. Whether that is safe is decided entirely by `computeUid`: with an `entry_reference` the identity is the bank's own immutable id, and **without one the uid is a hash that includes `normalizeDescription(description)`**. The stored uid is never recomputed — the danger is a *future* sync hashing the bank's description, failing to recognise a row already in the book, and appending a duplicate days after the edit with nothing pointing back at it. So `descriptionIsEditable_` is `source !== enablebanking`, and it is asked **twice**: by `recordForPage_` so the page knows whether to offer the field, and again in the writer, because a page can send anything. `crossSourceKey` — the imported/synced pairing behind "Remove synced duplicates" — reads no description at all, which was the other reason it might have had to say no.
- **The sign is never in the amount.** Direction is `credit_debit_indicator`, applied to `Math.abs(...)` — on transactions *and* independently on balances. Both are places where getting it wrong inverts a total while looking plausible.
- **Every report reads `amount_base`, never `amount`.**

## Testing

Tests go in the **same phase as the code they cover**, never batched at the end. The harness fakes the Google services, so it proves logic — not that Sheets accepts what we hand it. That gap is real: the locale `#ERROR!` bug passed every test. Things needing the live runtime go in `runSmokeTests()`, which writes to `_tests`.

`setup()` must stay idempotent, and must not discard user customisations — see `tests/customization.test.mjs` for the boundary.

**`src/page.html` is invisible to the harness**, because `node:vm` runs the `.gs` files and nothing inside an HTML file reaches it. That is not a gap to work around — it is the reason the aggregation lives on the server at all, and the reason to keep pushing decisions out of the page. What is left there is drawing, and the two things a *file* test can still prove about it are in `tests/manifest.test.mjs` and `tests/app.test.mjs`: that no string is assigned as markup, and that every name the page calls is a function that exists.
